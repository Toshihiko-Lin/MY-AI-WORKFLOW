## 为什么要这样用 AI？

你现在用 AI 的方式大概是：打开 ChatGPT 或 Claude → 输入问题 → 复制答案。这没什么问题，但 AI 其实可以做得多得多——**直接帮你改文件**、**知道你在做什么**、**记住你上次做到哪了**。

想象一下：AI 不是坐在网页对话框里等你粘贴内容，而是直接坐在你电脑桌面上，能自己打开文件、修改草稿、追踪任务进度。这份指南就是教你怎么做到这一步的。

## 三种入门方式，同一个目的地

无论你从哪里开始，目标是一样的：让 AI 直接操作你电脑上的文件，而不是在对话框里粘贴内容。

| 方式 | 特点 | 适合谁 |
|------|------|--------|
| **图形客户端** | 下载即用，拖拽文件，无需配置 | 想先感受能力、不想碰终端 |
| **IDE 插件** | 在 VS Code / Cursor 扩展市场直接安装 | 已经在用编辑器，想零摩擦接入 |
| **终端 CLI** | `claude` 或 `codex` 命令启动，无需打开 IDE | 希望 AI 直接调用 Obsidian 知识库、或不想打开 IDE 的轻量场景 |

三种方式调用的是同一个 AI，能力上没有差别。你可以从任何一种开始——图形客户端先试试感觉，IDE 插件直接上手，终端 CLI 一行命令启动，都行。

**本指南教的是哪种？**

这份指南从 Level 1 开始，逐步搭建**以 IDE 为中心的集成工作台**：AI 协作、文件编辑、Git 版本管理在同一个窗口里完成。如果你已经在用图形客户端或纯终端，Level 2–4 的规则文件和记忆管理对三种方式完全通用，可以直接跳过 Level 1。

**为什么最终要汇聚到 IDE 工作流？**

不是因为其他方式不够好，而是 **Git** 这个环节在独立 App 里断掉了。

使用图形客户端时，AI 在桌面 App 里改了文件，你要切到 VS Code 或另一个 Git 工具去提交版本。使用 IDE 时，这三件事在同一个窗口里同时可见：

```
┌─────────────────────────────────────────────────────┐
│  VS Code                                            │
│  ┌──────────────┐  ┌───────────────────────────┐   │
│  │ 文件资源管理器│  │  论文.md（正在编辑）       │   │
│  ├──────────────┤  ├───────────────────────────┤   │
│  │ Git 提交面板 │  │  Claude Code 侧边栏        │   │
│  │ • 暂存改动   │  │  > 帮我改一下第三章的措辞  │   │
│  │ • 填写说明   │  │  AI: 已修改，请查看 diff  │   │
│  │ • 一键提交   │  │                           │   │
│  └──────────────┘  └───────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

AI 改完，左边面板看 diff、点提交，不需要切换任何窗口。这种集成度是独立 App 提供不了的——不是 AI 能力的差异，而是 Git 和文件管理不在同一个地方。

### Git 是核心理由

**问题：你的文件夹现在长什么样？**

```
论文终稿.docx
论文终稿_改.docx
论文终稿_导师批注版.docx
论文终稿_打死都不改版.docx
论文终稿_打死都不改版2.docx
```

这是绝大多数人的现状。版本靠文件名区分，改动历史靠记忆，换电脑或协作时一团乱。

**Git 解决的问题：**

```
论文.md          ← 只有一个文件，永远是最新版
                  ← 历史每一稿都在版本记录里，可以随时回溯
                  ← 每次修改附带说明："补充实验二数据"
```

除了版本管理，**写文档使用 Markdown 而非 Word**，也是配合 AI 工作的关键。

**为什么不推荐继续用 Word？**

Markdown 的设计前提是：**写什么**和**长什么样**应该分开管理。写作阶段只关心内容，格式在最终输出时才介入。`.docx` 把两件事混在一起，是下面三个问题的共同根源。

`.docx` 不是文本文件，是一个伪装成文档的 ZIP 压缩包，里面是 XML 代码加图片资源。Claude Code 和 Codex CLI 在你的文件系统里工作，遇到 `.docx` 就像遇到乱码——它们能"打开"，但看到的不是你写的内容，而是 Word 用来描述格式的标签。

实际后果有三个：

- **精确性**：你说"帮我改这篇论文的第三章"，AI 要先穿透 XML 标签才能定位内容，改动也难以精确写回——你会退化回手动复制粘贴，和网页版 AI 没有本质区别。
- **Token 消耗**：AI 读 `.docx` 时，格式标签和实际内容一起计入 token。同样一篇论文，`.docx` 的消耗可能是 `.md` 的数倍。写作阶段用 Markdown，是节省额度最直接的方式。
- **版本管理**：Git 对 Word 文件几乎失效——它能记录"这个文件改了"，但无法显示改了哪几行、改了什么，因为 `.docx` 是二进制格式。

---

**如果你必须坚持用 Word**

有些情况确实无法回避 Word：期刊投稿要求 `.docx`、导师批注依赖 Track Changes、和不懂 Markdown 的人协作。这种情况下建议这样处理：

- **用网页版或桌面 App 客户端**：把 Word 内容复制进对话框，AI 返回修改后的文字，再粘贴回 Word。这是网页版 AI 的原生用法，体验是匹配的，不要强行套用 CLI 工作流。
- **分离写作和排版**：用 Markdown 起草、修改、迭代（享受 AI 深度协作和 Git 版本管理），最终提交前用 [Pandoc](https://pandoc.org/) 一行命令转换成 `.docx`。格式细节在转换后再调整。
- **混合使用**：主体内容在 Markdown 里用 AI 打磨，图表、参考文献、最终排版在 Word 里完成。这是可行的过渡方案。

如果你的场景是"我写的东西最终必须是 Word 文件"，**分离写作和排版**是最值得投入的路径：写作阶段不需要 Word，排版才需要。

IDE 与 Git 的集成是原生的。独立的 App 客户端适合一次性对话，但无法提供这种单窗口集成体验。

---

**常见顾虑**

**"我不用 GitHub，也没有服务器，Git 对我有用吗？"**

Git 和 GitHub 是两件事。GitHub 是一个网站，用来把代码上传到云端、和别人协作。本指南用的 Git 是本地版本控制——所有记录只存在你自己的电脑上，从来不联网，也不需要注册任何账号。你可以把它理解成给文件夹装了一个时光机：每次想存档就点一下，随时能回到任意一个历史版本。

**"我不想学 Git 命令。"**

不需要。VS Code 左侧有一个 Source Control 面板，点三下完成一次存档：勾选改动的文件 → 填一句说明 → 点提交。整个过程不需要打开终端，不需要输入任何命令。

**"我就是不想碰 Git，图形客户端 + Word 对我来说够用。"**

这是合理的选择。如果你的场景是偶尔让 AI 看一段文字、改改措辞，图形客户端配合复制粘贴完全够用，不需要这套工作流。本指南的 Level 2–4（规则文件、记忆管理）对图形客户端同样适用，可以直接跳过 Level 1，从 Level 2 开始读。

**"Markdown 没有 Word 直观，盯着符号写字对眼睛不友好。"**

这个感受是对的，不是误解。Word 的所见即所得在阅读和排版时确实更舒适。

但有两点值得知道再做决定：

第一，视觉差距比预期小。VS Code 内置 Markdown 预览，左边写、右边实时渲染，不是纯黑白符号。Obsidian 更接近所见即所得——打完 `**粗体**` 立刻显示成**粗体**，符号消失。实际写作体验和 Word 的差距，上手之后往往比想象中小。

第二，写作场景和阅读场景不同。Word 的视觉优势在"看最终效果"，而 AI 协作的核心场景是高频修改——AI 改了什么、改了哪里、能不能回退。这个场景下 Markdown 的纯文本反而更清晰，diff 一目了然。

如果你的主要工作是写完给别人看的长文档，且改动频率低，坚持用 Word + 图形客户端是合理的。如果是需要反复打磨、AI 深度参与的写作，Markdown 的取舍是值得的。

## 学习曲线：诚实的预期

这套工具组合对大多数人来说是陌生的。不是"稍微学一下"那种陌生，而是**三件新东西同时出现**：

- **Markdown**：不是 Word，没有格式栏，用符号写格式
- **IDE（VS Code）**：不是记事本，界面复杂，左边一堆面板
- **Git**：版本控制系统，有一套专门的概念（commit、branch、push…）

同时接触三件陌生事物，感到压力是正常的。这里需要说清楚两件事：

**第一，你需要的只是每个工具的最小子集。**

| 工具 | 你需要学的全部 | 你不需要碰的部分 |
|------|--------------|----------------|
| Markdown | `# 标题` `**粗体**` `- 列表`，10 分钟够了 | 复杂表格、HTML混排、各种扩展语法 |
| VS Code | 打开文件夹、写字、在侧边栏与 AI 对话 | 插件生态、调试器、各种配置 |
| Git | VS Code 左侧 Source Control 面板，点三下完成提交，不需要打开终端 | branch、merge、rebase、冲突解决 |

AI 交互通过 IDE 插件直接在侧边栏完成，Git 面板也完全内置在 VS Code 里——整个工作流不需要打开终端。

这四个"最小子集"放在一起，是一两个下午能摸清楚的量。

**第二，学习过程中 AI 是你的老师，不只是工具。**

你可以在任何时候问：
```
我想把这个文件夹的修改保存成一个版本，用 Git 怎么操作？
```
```
这行 Markdown 怎么写居中？
```

不需要先系统学完再开始用。遇到不会的随时问，边用边学比看教程有效得多。

**心理上最难的关口**不是技术，而是"我写了半小时论文，现在要先搞定这堆工具才能开始用 AI"的挫败感。这份指南的设计是：**每一步都有即时收益**。装完 VS Code 就能用，装完 AI 工具就能改文件，Git 之后再学也不晚——不是非要全部到位才能开始。
